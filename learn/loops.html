Loops

sproutJun 20266 min read

Here's your monthly reminder that you shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents.

I don't know about you, but that memo took a while to reach me.

I had seen loops before. The Ralph loop in particular made me think agents could do real work over time instead of one shot. You put a goal and a while loop around the agent and let it iterate. It was exciting. It was also a mess. Error rate went up fast because the loop had no memory of what mattered, no real verifier, and no isolation. Cool demo. Not much shipping.

So I went back to what I knew. Ask for a plan. Read it. Say go do part one. Part two. Spin up another agent for review. Copy the feedback back by hand. I was the loop. I was carrying context, deciding order, making sure nothing fell through. It worked, but it did not scale with me.

Then Pete's post landed. He has been ahead on this for a long time. I used to think of him as the guy running weird experiments so the rest of us could see what the future might look like in duct-tape form. I still do in some ways. But I started paying attention when he talked about getting agents to prompt themselves, setting up watchers that review code and trigger their own re-reviews, worktrees that monitor specific PRs or issues, and letting the system run while he slept.

Boris Cherny, who built Claude Code at Anthropic, said something almost identical around the same time: he does not prompt Claude anymore. He has loops running that prompt Claude. His job is to write loops.

Addy Osmani named the practice "loop engineering" and laid out the shape that keeps showing up across tools. That is when it clicked for me.

What changed

Before, the agent was a very fast junior I had to supervise turn by turn. Now I can give it a goal, a place to work that will not collide with anything else, some written rules it reads every time, and a way to check its own work. Then I walk away.

The loop does the discovery, the execution, the observation, the verification, and the decision to continue or stop. I design the loop and I decide what "good" means.

The pieces that actually matter

A loop is not just "run the agent again." It needs six things that live outside any single model call.

A heartbeat. Something that wakes up on a schedule or a trigger. Cron, a /loop command, a GitHub webhook, a simple timer in whatever tool you use. Without this it is just one manual run.

Isolation. Git worktrees or per-thread checkouts. The transcript that changed how I thought about this put it plainly: once the code for this PR lives in its own directory, you stop caring if the agent makes a mess there. Other work is not blocked. Two agents can run at once without stepping on the same files.

Memory that survives the call. The model forgets between runs. The filesystem does not. Write plans as HTML files so you can read them on your phone at 3am. Keep a progress log. Use something like AGENTS.md or SKILL.md at the root so every fresh agent starts with the real conventions instead of guessing. The repo remembers. The context window does not.

Skills and rules written down once. The conventions. The "we never do X because of that one incident." The checklist for a good PR here. Put it in a file the agent is told to read. You stop paying the "explain the whole project" tax on every iteration.

A verifier that is not the writer. The model that just edited the code is the worst possible judge of whether the edit is correct. Split them. Use a second sub-agent, a different model, or at minimum a /goal step where a fresh pass checks explicit conditions (tests pass, lint clean, matches the spec in the plan file). Maker and checker.

Connectors to the real world. The loop is only useful if it can open the PR, leave a comment, update the issue, run the deploy command, or send the message when it is done. Tools that only talk to the filesystem are toys. The ones that can act in your actual environment are the ones that compound.

A small loop

Every night a heartbeat runs on this repo. It calls a small triage skill that looks at open issues and recent commits, writes a short markdown summary, and for anything small and safe it opens an isolated worktree, lets an agent make the change, runs the trivial checks that exist, and opens a draft PR with the plan file attached. I get a notification. Most nights nothing happens. When something does, the diff is small and I can review it in a minute.

I did not write a prompt for "go look at issues." I wrote the heartbeat, the skill file, the rule that changes must be tiny, and the stop condition. The loop does the rest.

A larger one

The one that really landed for me was bigger than one PR. I had a chunk of work that was clearly three or four stacked changes. I asked the agent to break it into plans as HTML files. Then I sent one message: spin up a thread to implement the first plan and file the PR, spin a review thread when the PR appears, put that review thread into a loop that watches for comments and addresses them until it gets approvals, merge when green, pull main, and start the next chunk.

It made a diagram. It used a heartbeat attached to the monitoring thread. It did the work. I went to sleep. I woke up with four stacked, heavily reviewed PRs ready. It was not fully autonomous and I am not claiming it was. I still set the goal and the definition of done. But the handoff between the pieces and the comment chasing happened without me copy-pasting.

That was the taste. Now I look for other places where the same shape applies.

Ralph was the prototype

Geoff Huntley's Ralph loop was the simple ancestor: fresh context every iteration, external files for the goal and progress, a dumb while loop around the agent. It proved you could get an agent to keep working on something bigger than one prompt. It also proved that without isolation, without a real checker, and without good memory, the error rate makes the thing expensive and fragile. Every serious loop since has kept the "fresh context + external state" idea and added the missing guardrails.

What is still on you

The loop does not remove the engineer. It removes the part of the job that was mostly drudgery.

You still choose the goal. You still write the stop condition that actually matters for this project. You still read enough of the output to keep your understanding current. You still apply taste. "Good ideas still need human ingenuity," as Pete put it. If you treat the loop as a way to stop thinking, you will get code you do not understand and a system you cannot steer.

Verification is the price of walking away. If the checker is weak, the loop just produces more confident mistakes.

How to start

Pick one repetitive thing you already do by hand. Triage failures. Keep a dependency up to date. Apply a standard refactor. Write the success criteria first and put them in a file next to the code. Give the agent a worktree or a branch that cannot collide with anything live. Add one explicit review or test gate. Run the loop while you are still watching the output. Only then let the heartbeat own the night.

Write the rules down before you are tired of explaining them. The first version of the SKILL.md or AGENTS.md will be wrong. That is fine. You edit the rules the same way you edit any other code.

Start small. One loop. Make it boring. Make it reliable. Then notice what else is now obvious to automate the same way.

Same principles as everything else

This is not a new religion. It is the same ideas that make the rest of the work on this site work. External state over in-memory magic. Isolation so things can fail safely. Written rules instead of tribal knowledge. A verifier that is not the implementor. Boring tools that stay out of the way. Delete what you can. Keep the leverage and the ownership.

The agents are not going to design the loops for you yet in a way you would trust for real work. You still have to do that. But once the loop exists, a lot of the prompting disappears. You stop being the pager. You become the person who writes the system that pages the agents.

That feels like the right direction.
