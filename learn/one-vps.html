Everything on one box

sproutJun 20265 min read

One small ARM box runs almost everything I have built. A handful of projects on a single server that idles most of the time. It has been up for four months without a reboot, sitting at a third of its disk with most of its memory free.

People assume this needs orchestration. Kubernetes, a CI platform, a container registry, a managed database. It does not. It needs a reverse proxy and a habit.

The front door

Every request hits Caddy first, and Caddy is the only thing on the box bound to a public port. It terminates TLS, fetches and renews certificates on its own, and routes each hostname to a process listening on localhost. No certbot, no renewal cron, no remembering to renew anything. I write down a domain, Caddy gets the cert.

Caddy itself runs as a container in network_mode: host, so it binds :80 and :443 directly with no port mapping in the way. A named volume holds its ACME account and issued certs, so rebuilding the container never re-fetches a single certificate.

services:
  caddy:
    build: .
    network_mode: host
    restart: unless-stopped
    volumes:
      - caddy_data:/data            # ACME account + certs survive rebuilds
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - ./www:/srv/www:ro

volumes:
  caddy_data:

One Caddyfile is the single source of truth. The host path is a symlink to it, so caddy reload through the admin API on :2019 hot-swaps the config with no dropped connections, and the container loads the exact same file on restart. Two load paths, one file.

The file itself stays small. A static site is a folder. An app is a port. A streaming endpoint just needs buffering turned off.

static.example.com {
    root * /srv/www/site
    file_server
    encode gzip
}

app.example.com {
    # static shell + an API backend, both under one host
    handle /api/*/stream {
        reverse_proxy localhost:4000 {
            flush_interval -1         # do not buffer server-sent events
        }
    }
    handle /api/* {
        reverse_proxy localhost:4000
    }
    handle {
        root * /var/www/app
        file_server
    }
    encode gzip
}

I keep the hostnames explicit and resist the urge to add a wildcard catch-all. I tried on-demand TLS for arbitrary subdomains once; bots probed random names and Caddy dutifully tried to issue a certificate for each one. A named list never has that problem.

Two ways to run a thing

Every project on the box is one of two shapes.

If it is already containerized, it is a docker-compose.yml in its own folder.

services:
  app:
    build: .
    ports:
      - "127.0.0.1:3000:3000"       # localhost only, never 0.0.0.0
    env_file: [.env]
    volumes:
      - ./data:/app/data
    restart: unless-stopped

If it is not, it is a systemd unit. Same idea, less Docker, with a little more care around startup order and shutdown.

[Unit]
After=postgresql.service network.target
Requires=postgresql.service          # do not start before the database

[Service]
WorkingDirectory=/opt/app
Environment=DATABASE_URL=postgres://app:app@localhost/app
ExecStart=/opt/app/.venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000 --timeout-keep-alive 300
Restart=always
RestartSec=5
KillSignal=SIGINT                    # let it drain in-flight requests
TimeoutStopSec=10

[Install]
WantedBy=multi-user.target

Both end the same way: a process bound to localhost, ordered after its dependencies, restarted on failure, fronted by Caddy. Docker or systemd is just a detail of how the process gets started. The shape of the system does not change.

Nothing else faces the internet

This is the part that makes the whole thing safe to leave alone. Caddy owns :80 and :443. Everything else, every app, every worker, the database, binds 127.0.0.1. Nothing is reachable from outside except through the reverse proxy, so the firewall is almost a formality. You cannot attack a port that was never published.

The database is just there

Postgres runs on the box. Not in a container, not managed, not a separate thing I pay for. It listens on 127.0.0.1 only, and apps reach it at localhost over a loopback connection. The systemd units declare Requires=postgresql.service, so nothing tries to talk to a database that has not started yet.

The backup is a pg_dump on a timer. One command, one file, copied off the box. For the traffic I have this is plenty, and it will stay plenty for a long time.

Exposing my laptop

Sometimes I want a public URL pointing at something running on my own machine. A webhook target while developing, a quick demo, a service I do not want to deploy yet.

So my laptop opens an SSH reverse tunnel to the box. ssh -R 9000:localhost:3000 box parks a listener on the server's localhost that forwards back to a port on the Mac. Then it is just another Caddy site.

dev.example.com {
    reverse_proxy localhost:9000     # rides the tunnel to my laptop
}

Public HTTPS on one end, localhost on the other. A webhook hits the public URL, Caddy terminates TLS, and the request rides the tunnel down to a process on my desk. It is ngrok, except I own both ends and it costs nothing.

Deploying is boring

Pull the code, rebuild, restart. git pull && docker compose up -d --build, or git pull && systemctl restart app. Config-only changes to the proxy are a caddy reload, no restart at all. No pipeline, no registry, no waiting on a runner somewhere.

Boring is the point. The most exciting thing that should happen during a deploy is nothing.

What I don't run

No Kubernetes. No Terraform. No CI platform billing me by the minute. No service mesh, no load balancer, no autoscaler for traffic that fits in a corner of one CPU.

The box has been up for months, sitting at a third of its disk and a fraction of its memory. When one box is not enough, I will get a bigger box. That day is further away than you would think.
