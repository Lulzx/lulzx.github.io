# Story

I grew up with a very slow Pentium 4 computer. Opening a heavy program meant listening to the fan spin up and watching the cursor stall until the disk finished thrashing. On a machine like that, you learn early that software has weight. Every extra process, every background updater, and every careless megabyte takes time out of your day.

For a stretch after that, I did not have a computer at all. In 2017 I started writing Telegram bots on my phone. The first one replied to messages with random quotes and took about an hour to put together. I deployed it from the phone by SSH-ing into a $5 server and running `python bot.py`. When a process died at 3am from a timeout, garbage input, or an out-of-memory crash, I fixed it on the same small screen. That was where I learned to keep the queue, the cache, and the log outside a single run so a restart could pick the work back up without dropping a night of messages.

## Four gigabytes on a ThinkPad E480

Later I got a ThinkPad E480 with 4 GB of RAM. Four gigabytes left no room for a heavy desktop operating system, so I moved to Linux out of necessity. If the system ate two gigabytes at idle, I had nothing left for the browser, the editor, and the code I was trying to run.

That constraint pushed me through different Linux distributions and deep into how the operating system was put together. I stripped out services I did not need, watched memory numbers in a terminal, and switched to a tiling window manager. A tiling desktop gives every window a slice of the screen instead of letting them stack into a pile. One pane held the file I was editing, one held the test output, and one held my notes. Living inside 4 GB taught me to check what a tool costs before inviting it onto the machine.

## Search, distribution, and the wrapper detour

With a working Linux setup and a $5 VPS, I spent the next few years building things a single person could run end to end. In 2018 I rewrote my Python bots in Node.js and learned the hard way what nested callbacks do to a codebase. Between 2019 and 2020 I got pulled into information retrieval: indexing Telegram archives in [discover](https://github.com/Lulzx/discover), building a quiet book search interface in [shoten](https://github.com/Lulzx/shoten), and experimenting with vectors, embeddings, and HNSW nearest-neighbor search in [sentence-similarity-search](https://github.com/Lulzx/sentence-similarity-search) before the rest of the industry started calling all of that work AI. Alongside the search tools, I built automated Telegram deal and price-tracking pipelines that had to stay up under real traffic. In 2021 I burned out, wrote nothing for three months, and came back clearer.

In 2023 I picked up Rust to rewrite my command-line tools. The compiler forced me to name the owner, the error, and the lifetime before the first happy path would build. In 2024 I tested the standard startup and agency playbook: Nuxt and Vercel AI wrappers, content-repurposing pipelines, autonomous agent templates, DeFi liquidation bots, and smart-contract bug bounties with [immunefi-cli](https://github.com/Lulzx/immunefi-cli). That stretch taught me what I actually cared about. Gluing heavy JavaScript stacks onto remote APIs felt fragile and hollow. By contrast, finding a real replay bug in a protocol or keeping a bot alive at 3am rewarded reading the raw source and verifying every invariant from first principles.

## Rebuilding the black boxes

Once I walked away from wrapper code, I started opening the boxes I had been told to treat as finished infrastructure. Every time a tool felt bloated or opaque, I asked how many lines the actual mechanism took if I threw away the framework.

To understand compilers and virtual machines, I wrote a C compiler from first principles in [sectorc](https://github.com/Lulzx/sectorc), a Zig implementation of the interaction-calculus runtime in [hvm](https://github.com/Lulzx/hvm), self-hosting compilers for [Arturo](https://github.com/Lulzx/arturo-compiler), [J](https://github.com/Lulzx/tacitj), and [Bend 2](https://github.com/Lulzx/bendc), a tracing JIT for Wren in [WrenJIT](https://github.com/Lulzx/WrenJIT), an array-scheduling operating system in [tacit](https://github.com/Lulzx/tacit), and minimal virtual machines for Erlang BEAM ([beam.zig](https://github.com/Lulzx/beam.zig)) and TON ([zig-tvm](https://github.com/Lulzx/zig-tvm)). To strip machine learning down to the metal, I wrote reverse-mode automatic differentiation on plain NumPy in [nabla](https://github.com/Lulzx/nabla), a neural network in roughly 600 lines of Zig in [nn.zig](https://github.com/Lulzx/nn.zig), and a fast BPE tokenizer core in Rust in [blaze-bpe](https://github.com/Lulzx/blaze-bpe).

I applied the same rule to everyday files and physical hardware. [tinypdf](https://github.com/Lulzx/tinypdf) creates real PDFs in under 400 lines of TypeScript with zero dependencies, paired with [zpdf](https://github.com/Lulzx/zpdf) for zero-copy SIMD text extraction in Zig, [zs3](https://github.com/Lulzx/zs3) for zero-dependency S3 storage, and [walsync](https://github.com/Lulzx/walsync) for streaming SQLite write-ahead logs across machines. When I bought a Brother HL-L2440DW laser printer, I reverse-engineered its compressed 1-bit raster format and wrote a 400-line C program ([brother-hl-l2440dw](https://github.com/Lulzx/brother-hl-l2440dw)) to print over raw TCP without Brother's driver. When I fought a dead programmer on an AI-Thinker ESP32-CAM, I wrote self-contained MJPEG streaming firmware ([esp32-cam-web-streamer](https://github.com/Lulzx/esp32-cam-web-streamer)) that serves video straight to any LAN browser with no cloud account. When I wanted a 3D-printed part to fit an irregular opening on the first print, I built [reality-fit](https://github.com/Lulzx/reality-fit) to go from a 10-second webcam scan next to a paper marker straight to a fitted mesh.

## Refusing hardware ceilings

In 2024 I moved my daily work onto Apple Silicon. On my old setups, every GPU workload paid a copy tax across the bus. Unified memory meant the CPU and GPU shared one pool of RAM, so a 14-inch laptop could hold weights and run passes that used to require a remote server.

The reflex from the 4 GB ThinkPad came right back: make the local machine do what people assume needs a cluster. I built a CUDA compiler and runtime for Apple Silicon GPUs in [cuda-metal](https://github.com/Lulzx/cuda-metal), emulated double-precision arithmetic on Metal GPUs that lack hardware FP64 in [VF64-metal](https://github.com/Lulzx/VF64-metal), and brought scientific solvers like GROMACS ([gromacs-metal](https://github.com/Lulzx/gromacs-metal)), WarpX plasma simulations ([warpx-metal](https://github.com/Lulzx/warpx-metal)), PeleLMeX combustion ([pele-metal](https://github.com/Lulzx/pele-metal)), and Box3D physics ([box3d-metal](https://github.com/Lulzx/box3d-metal)) onto the M-series GPU. For language and speech models, I wrote fused Metal kernels in Zig with no Python or PyTorch ([tiny-kernel](https://github.com/Lulzx/tiny-kernel)), ran a 2-bit 27B model locally at 20 tokens per second ([bonsai-mlx](https://github.com/Lulzx/bonsai-mlx)), and pushed full speech recognition ([phonon-web](https://github.com/Lulzx/phonon-web)) and language models ([barunlm-35m-browser](https://github.com/Lulzx/barunlm-35m-browser)) entirely into the browser over WebGPU and WebAssembly.

## Where the work is going now

After rebuilding compilers, virtual machines, and GPU kernels from scratch, the questions I care about shifted. Three threads run through almost everything I am building now.

The first thread is learning through compression, search, and proof instead of brute-force scale. Scaling a transformer is expensive, and an unverified model will cheerfully invent a plausible lie. In [solon](https://github.com/Lulzx/solon), I built a language learner around Minimum Description Length with no transformer, no gradients, and no backpropagation, testing how far pure compression goes in a low-data regime. In [supsearch](https://github.com/Lulzx/supsearch), [ontogenesis](https://github.com/Lulzx/ontogenesis), and [progen](https://github.com/Lulzx/progen), program synthesis engines solve benchmarks and invent reusable lambda-calculus vocabulary without calling a language model. In [gavel](https://github.com/Lulzx/gavel), reinforcement learning policies are scored by Bend's proof checker rather than a learned reward model that can be gamed. The same insistence on machine-checked truth drives [open-magnetar](https://github.com/Lulzx/open-magnetar), a post-quantum RV64I zero-knowledge VM over binary fields using only standard hashes, and [claim-wire](https://github.com/Lulzx/claim-wire), an incremental compiler that treats every number in a Markdown document as a typed build target traceable to the run that produced it.

The second thread is compiling living and physical systems into runnable, differentiable code. Once you have a fast simulator and exact gradients, you can treat biology and physics like programs you can inspect and perturb. In [fly-brain](https://github.com/Lulzx/fly-brain), the complete 165,122-neuron, 104-million-synapse connectome of a fruit fly runs as a spiking brain inside a physics-simulated body in the browser, separating which behaviours emerge from the wiring diagram alone and which require rules from outside the graph. In [worm-sim](https://github.com/Lulzx/worm-sim), [occam-worm](https://github.com/Lulzx/occam-worm), and [molecular-compiler](https://github.com/Lulzx/molecular-compiler), connectomes and molecular profiles of *C. elegans* are compiled into differentiable simulations to search for compact local neural update rules that predict causal responses in unseen animals. That same first-principles simulation work extends to whole *E. coli* cells ([life-sim](https://github.com/Lulzx/life-sim)), magnetic nozzles and tokamak plasma ([helicon](https://github.com/Lulzx/helicon), [driftmap](https://github.com/Lulzx/driftmap), [plasma-tsu-tomo](https://github.com/Lulzx/plasma-tsu-tomo)), GPS-denied drone swarms ([skein](https://github.com/Lulzx/skein)), urban microclimates ([urbancool-jax](https://github.com/Lulzx/urbancool-jax)), and lithium-ion battery degradation ([BatteryUDE.jl](https://github.com/Lulzx/BatteryUDE.jl)).

The third thread is autonomous software guarded by hard deterministic boundaries. When I build agent environments like [helium](https://github.com/Lulzx/helium), [carry-terminal](https://github.com/Lulzx/carry-terminal), and [mimo-build](https://github.com/Lulzx/mimo-build), capability sandboxes like [caplock](https://github.com/Lulzx/caplock), declarative deployment engines like [alchemy-celld](https://github.com/Lulzx/alchemy-celld), or self-running media and commerce pipelines, the rule stays the same one I learned on my phone in 2017: never let a probabilistic step hold state or custody. Deterministic code owns the log ([memo](https://github.com/Lulzx/memo)), the grammar ([typed-inference](https://github.com/Lulzx/typed-inference)), the permissions, and the verification gate.

I opened this repository in September 2017 with the description "My website to tell my story." The machines got faster and the problems moved from quote bots on a phone screen to compilers, GPU kernels, and whole-brain connectomes, but the bias never changed: keep the footprint small, read the source, and own the stack from the bytes up.
